# Project Foundation

## 目标

把一份已经确认的产品设计转换成可开发的仓库基座。完成后，第一次接手项目的维护者能够从仓库回答：

1. 产品最终交付什么；
2. 系统由哪些可以独立设计和验证的模块组成，每个模块交付什么、谁使用；
3. 模块之间交接什么，依赖方向怎样；
4. 每个文件和事实由谁负责；
5. 代码、测试、文档、配置和本地产物放在哪里；
6. 怎样检查一项变更是否完成；
7. 当前实现与目标还差什么；
8. 下一项能够直接执行的工作是什么。

只建立进入功能开发所需的结构。功能模块设计和实现从当前开发计划继续。

## 为什么这套结构能让项目进入开发

### 一个结果，一个负责人

软件会反复修改。同一项内容由多个地方定义时，每次变化都要同步多个位置，遗漏一个就会产生冲突。

因此，让每项产品结果、公共契约、文件位置、验证规则和当前状态只有一个负责来源，其他文档链接到这个来源。后续修改只需要找到一个入口。

### 分开目标、现状和差距

目标和现状混在一起时，会出现两种错误：按当前代码缩小尚未实现的目标，或者把计划写成已经可用的功能。前者失去方向，后者失去真实状态。

因此，系统设计和模块设计描述已经确认的目标；代码、配置、测试和实际运行结果描述已经实现的事实；当前开发计划描述两者之间仍未解决的差距。

### 让模块成为可组合的积木

目录和技术分层只是组织方式。模块是一块能够独立交付结果的软件积木：它有明确使用者、稳定输入输出和失败边界，并且可以独立设计和验证。

只有具备独立结果的职责才建立模块。这样增加的每个模块都能独立工作，而不是增加新的协作负担。

因此，先按产品结果划分模块，再固定公共数据、运行链路和依赖方向。总设计只规定这些外部边界，模块实现者决定内部算法、文件拆分和工具选择，其他模块不依赖它的内部实现。

### 用实际结果支撑结构与计划

只阅读设计和代码，不能证明命令真的可运行、外部工具真的按预期工作、已有行为没有被破坏。没有实际结果，计划中的差距和完成判断都可能只是猜测。

因此，修改前后都运行与当前风险相称的检查；仓库事实由文件、配置、命令或实际运行证明；外部技术事实由官方来源和真实运行确认。

### 当前计划让下一位维护者直接继续

长期设计说明最终要到哪里，Git 历史说明过去发生了什么，但两者都不能直接回答眼下从哪里继续。

因此，当前计划只保存目标链接、剩余差距、剩余阶段、当前阶段和下一行动。阶段完成后，由代码、设计、配置或测试继续记录结果，计划只维护剩余工作。

### 少量真实结构比完整外观更容易维护

每个文件、目录、接口和依赖都要在以后被理解、验证和修改。空模块和占位文件增加维护对象，却没有交付结果，还会掩盖真正缺失的工作。

因此，先确认职责、使用者和交付结果，再建立文件和目录；只创建当前有真实内容的模块、测试和配置。

## 执行边界

用户主动调用本 skill，即授权在当前仓库检查、建立并验证符合下面要求的项目基座。

授权范围是进入功能开发所需的仓库结构。产品功能实现以及发布、推送、删除用户数据等不可逆外部操作属于后续任务。

系统方向缺少关键决定时，只请用户确认会改变产品目标或公共边界的问题。其余实现方法根据已经确认的设计和仓库结构继续完成。

## 第一步：检查仓库

先读取：

- 项目级代理规则；
- 用户指定的产品设计和现有架构文档；
- README、构建配置、包管理配置和工具配置；
- 当前源码、测试和文档入口；
- Git 工作区状态。

把开始工作前已经存在的修改视为用户输入。记录这些文件，只在本次授权范围直接需要时修改；无法与基座改动分开时，先说明冲突和风险。

运行现有的最低成本检查，记录修改前结果。

### 判定项目起点

项目起点决定可以复用什么、差距从哪里开始；它不降低最终基座标准。按仓库已经存在的内容选择最接近的一项：

1. **空目录**：没有有效仓库文件，产品方向来自用户提供的外部设计；
2. **设计阶段**：已有产品、RFC 或系统设计，没有工具链和产品代码；
3. **工具链空壳**：已有构建配置、最小入口或 smoke test，没有产品行为；
4. **原型阶段**：已有能够演示的行为，职责、数据或依赖边界尚未稳定；
5. **部分实现阶段**：部分目标模块已经实现并有检查，其他模块仍是差距；
6. **成熟项目阶段**：主要产品行为、工具链和检查已经稳定，只需补全或统一基座职责。

### 检查同时存在的问题

同一个项目还可能同时出现以下问题：

- 设计存在职责混合、共享可变状态、内部依赖或循环依赖；
- 目标设计与当前实现交付不同结果；
- 多个文档或配置同时定义同一事实；
- 代码能够运行，但产品方向、设计或维护边界不可信；
- 当前架构与已经确认的新版本目标同时存在；
- monorepo（一个仓库包含多个独立交付的包或服务）中的交付范围各自发布、验证或推进；
- 开始工作前存在本次任务之外的修改。

### 根据起点调整工作

- 空目录和设计阶段从已确认的产品方向建立搭积木架构和文档基座。已确认的工具链进入结构设计，仍需用户决定的技术选择先完成确认；
- 工具链空壳继续使用现有语言、构建、包管理和测试入口；
- 原型和部分实现阶段保留已经验证的行为，把当前结构与目标模块之间的具体差距写入计划；
- 成熟项目继续使用现有权威来源、文件位置和稳定命令，只补全缺失职责；
- 设计不符合搭积木要求时，先按第二步校准；
- 设计漂移和架构演进分别由设计记录目标、运行结果记录现状、当前计划记录迁移差距；
- 权威来源冲突和遗留项目先恢复可信事实，再为每项事实确定一个负责人；
- 多交付范围共享仓库级规则，每个独立交付范围维护自己的当前计划；
- 已有工作区修改保持原意，并与本次基座改动分开。

分类只服务本次执行。长期文档保存已经确认的目标、能够验证的实现事实和仍需行动的具体差距。

最后把调查结果分成：

1. 已经确认的目标；
2. 仓库已经实现的事实；
3. 目标与实现之间的差距。

仓库事实用文件、配置、检查命令或实际运行结果证明。复用已经承担明确职责的文档、目录和命令。

框架、SDK、CLI、包管理器和云服务的当前行为以官方文档、公开类型、源码和实际运行结果为准。运行当前环境能够执行的命令；其余待确认行为作为差距进入当前计划。

语言、框架或工具链的选择会改变产品边界、公共接口或长期维护方式时，由用户确认。其他方法根据已确认约束决定；默认结构沿用已经确认的工具链。

## 第二步：把系统设计校准成可组合模块

用户给出的设计是产品方向和已确认约束的权威来源。模块划分和文件结构从这些内容推导。先提取并保留：

- 产品为什么存在，最终交付什么；
- 产品范围和明确不负责的内容；
- 对外接口、数据所有权、安全边界和结果保证；
- 已经确认且会约束实现的条件。

然后把实现架构转换成搭积木结构。目标系统设计必须直接说明：

- 运行模块及每个模块独立交付的结果和使用者；
- 每个模块的输入、成功结果、失败结果和边界情况；
- 跨模块公共数据或接口及其唯一负责人；
- 主要运行链路和模块依赖方向；
- 全系统必须守住的结果。

模块划分同时满足：

- 每项结果只有一个负责模块；
- 模块通过已经定义的输入输出协作，内部状态和内部文件只服务本模块；
- 每条依赖都能由运行链路解释，整体依赖关系具有清楚方向；
- 每个模块能够独立设计、实现和验证；
- 只有具备独立交付结果的职责才建立模块。

发现输入设计不符合这些条件时，按问题性质处理：

1. 已确认事实足以补全的缺失内容，直接补全；
2. 技术分层、共享可变状态、循环依赖或职责混合等实现方法问题，在保留产品方向和公共承诺的前提下重组；
3. 重组会改变产品结果、对外接口、数据所有权、安全边界或结果保证时，说明冲突、可选方向和各自影响，让用户决定。

现有系统设计文档继续承担权威职责，并在原位置完成校准。现有代码与目标设计不一致时，代码记录当前实现，设计保持已经确认的目标，当前计划记录两者差距。

系统设计满足上述条件后，继续建立结构职责、文档和物理边界。方向冲突尚未解决时，本步骤的交付结果是清楚的冲突说明、可选方向和待用户确认的问题；确认后从这里继续。

## 第三步：建立四项结构职责

持续开发需要稳定回答四类问题：文档由谁负责、文件放在哪里、怎样判断完成、下一步做什么。

Documentation、Project Structure、Verification 和 Development Planning 分别回答这四类问题。它们是项目基座必须具备的结构模块。

每个结构模块都有独立设计和唯一权威文档。

已有仓库中，职责完整、边界清楚的文档可以一对一承接对应结构模块。缺少承载点时使用默认布局。文件名和路径沿用仓库约定；每份文档只负责一个结构模块，每个结构模块只有一个权威来源。

### Documentation

规定文档类型和位置、每项内容的唯一来源、模块设计要求、文档入口，以及文档建立、更新和删除条件。

### Project Structure

规定源码、测试、文档、配置和本地产物的位置，源码模块公共入口，跨模块导入边界，以及目录和模块的建立、删除条件。

### Verification

规定各层检查证明什么、项目稳定检查命令、检查结果怎样解释，以及什么结果表示一次变更完成。

先区分当前已经能够运行的命令和目标设计中的未来命令。当前设计把未来命令写成目标，当前计划把它记录为尚未实现的差距。

### Development Planning

规定怎样从目标和实际差距建立当前计划，怎样安排阶段、选择下一行动、处理偏差和阻塞，以及计划怎样完成、替换和删除。

## 第四步：建立最小文档结构

沿用仓库现有文档位置。项目没有稳定约定时，使用以下默认布局：

```text
README.md
AGENTS.md
docs/
├── README.md
├── design.md
├── development-plan.md
└── modules/
    ├── documentation.md
    ├── project-structure.md
    ├── verification.md
    └── development-planning.md
```

默认布局按下面方式分配职责：

- `README.md` 是仓库入口；
- `AGENTS.md` 告诉开发代理先读哪些设计和当前计划；
- `docs/README.md` 导航当前计划和长期设计；
- `docs/design.md` 负责系统目标、运行模块、公共契约和依赖方向；
- `docs/development-plan.md` 负责默认单一交付范围的当前计划；
- `docs/modules/` 保存独立模块设计。

已有仓库继续使用稳定路径。基座阶段建立四个结构模块设计；当前计划进入某个功能模块的设计阶段后，再为该模块建立独立设计和目录。

## 第五步：写模块设计

每份模块设计都要让第一次接触项目的维护者回答：

1. 这份文档独自负责什么，什么变化要求更新它；
2. 模块为什么存在、独立交付什么结果、谁使用；
3. 模块接收什么，负责哪些公共数据；
4. 成功、失败和边界情况分别交付什么；
5. 模块负责什么、不负责什么，相关职责由谁负责；
6. 模块依赖什么，谁可以依赖它；
7. 哪些公共边界必须稳定，哪些内部实现可以自由变化；
8. 哪些事实能够独立证明实现符合设计。

长期模块设计保存已经确认的目标。当前实现事实和它与目标之间的差距由当前计划负责。

## 第六步：建立当前开发计划

先确定计划负责的独立交付范围，也就是能够独立确定版本、发布和验证结果的部分。

单产品仓库由 `docs/development-plan.md` 负责。monorepo 中独立交付的包分别维护当前计划。每个范围只有一份当前计划，并且都能从统一文档入口到达。

当前计划至少包含：

- 当前交付目标及对应的系统设计或模块设计链接；
- 本次范围和明确不做的内容；
- 由文件、配置、测试或实际运行结果支持的剩余差距；
- 按依赖关系排列的剩余阶段；
- 当前阶段和下一行动；
- 指向 Verification 完成条件的检查要求。

每个阶段说明前置条件、范围、交付结果和进入下一阶段的条件。前置结果交付后，依赖它的阶段开始；相互独立的工作可以并行。

阶段完成后，从计划中删除已经完成的步骤，根据实际结果重新确定剩余差距和下一行动。Git 是版本计划历史的唯一来源。

## 第七步：建立物理结构

把已经确认的模块职责映射到源码位置：

- 一个模块被其他模块调用时，提供符合当前语言和工具链习惯的稳定入口；
- 只有模块需要独立变化或整体替换时，才固定公共接口；
- 模块内部文件只服务本模块；
- 外部 SDK（第三方开发包）的类型由负责该 SDK 的模块管理；系统设计把它确定为公共契约时，其他模块按该契约使用；
- 其他跨模块数据使用项目自己的类型。

基座阶段由 Project Structure 记录计划模块的位置和入口规则，并检查当前已有源码是否符合边界。功能模块进入真实行为开发阶段时再建立源码文件。

真实源码交付当前行为。空函数、空类、占位返回值和只为形成目录而建立的入口文件都属于占位。

引入外部依赖前，说明它解决的当前问题、现有能力能做到什么，以及项目以后需要承担的维护成本。只有外部依赖带来当前所需且现有能力无法提供的结果时，才把它加入基座。

## 第八步：验证基座

以下列表是项目基座完成情况的唯一检查清单：

- 所有相对文档链接有效，每份长期设计都能从统一文档入口到达；
- 每项目标、实现事实和当前状态只有一个负责来源；
- 系统设计能够独立说明产品方向、公共承诺、模块关系和全系统保证；
- 每个功能模块都有独立结果、使用者、输入输出边界和独立验证方式；
- 模块依赖沿运行链路保持清楚方向，内部状态和内部文件只服务所属模块；
- Documentation、Project Structure、Verification 和 Development Planning 各有独立设计和唯一权威文档；
- 文档、源码、测试、配置和本地产物的位置已经确定；
- 计划模块的公共入口和依赖规则已经定义，当前已有源码符合这些规则；
- Verification 区分当前可运行检查与尚未实现的目标检查；
- 每个独立交付范围的当前计划与仓库事实一致，并有按依赖排列的阶段和能够直接执行的下一行动；
- 根 README 和项目代理规则指向正确入口；
- 所有新增内容都有当前读者和独立职责，仓库中没有空目录、空模块或非空占位；
- 仓库当前存在的检查已经实际运行，已有产品行为在修改前后保持一致；
- 外部技术事实能够追溯到当前官方来源或实际运行结果；
- 开始工作前已有的修改保持原意，并与本次基座改动分开报告；
- 仓库使用相对路径，完整复制后仍能工作。

检查未通过时，先判断原因属于本次修改、已有问题还是环境条件。本次修改造成且属于当前范围的问题在本次修复；其他问题以事实和影响进入当前计划与最终报告。

## 完成条件

第八步检查清单全部通过，最终报告列出校准后的搭积木架构、建立的基座、实际验证结果和下一行动时，项目基座完成。检查仍然失败或受阻时，最终报告说明当前结果和继续位置，项目基座保持未完成状态。

完成后停止。功能模块设计和实现按当前计划继续。
